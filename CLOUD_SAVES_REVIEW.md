# Облачные сохранения: проверка перед публикацией

Основной проект: bakery-empire-telegram, v33-tg. Публикация Pages: main, корень. Изменения подготовлены в feature/cloud-saves; production и Worker не изменены.

Добавлен отдельный клиент D1: GET/PUT /api/save, Authorization: tma initData, revision. Старый выбор по монетам/дате удалён. Игрок явно выбирает локальную или облачную версию; перед выбором создаётся локальная резервная копия. Запросы записи последовательны; конфликт останавливает запись до повторного чтения и выбора. Ошибка сети сохраняет ожидающий снимок, новые снимки имеют приоритет. Локальный save() сохранён.

Результаты: браузерный тест с имитацией Telegram и API прошёл: перенос, запись, конфликт revision, остановка записей, повторное чтение и восстановление. Проверка синтаксиса нового JS прошла. Публичный GET без авторизации возвращает Telegram authentication required. Это не проверка успешной записи D1.

Ограничения: доступна резервная копия Worker, а не подтверждённый экспорт текущего production. Worker не развёртывался и не изменялся. Реальные Telegram initData, D1 запись/чтение, два устройства, Android/iOS ещё не проверены. Серверный HMAC и поведение при повреждённых/слишком больших данных требуют отдельной проверки с тестовыми данными до production. Старые Telegram CloudStorage чанки сохраняются, автоматический импорт из них не включён. Статус синхронизации только на русском. Текущий UI выбора появляется при каждом запуске Telegram.

Финальная проверка: на отдельной тестовой копии Mini App и разрешённом тестовом аккаунте перенести локальный прогресс; открыть второе устройство и восстановить облако; одновременно изменить оба устройства и убедиться в явном разрешении конфликта; отключить сеть, продолжить игру, вернуть сеть и проверить запись; сравнить прогресс после повторного входа. Не использовать реальные сохранения игроков для теста.

Объединение PR и production требуют отдельного подтверждения Михаила.
